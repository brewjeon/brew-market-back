# 게시글 사진·임시저장 계약

## 목적과 파일

- `V6__post_images_and_drafts.sql`: 기존 한 장의 사진을 순서가 있는 사진 테이블로 옮기고, 임시저장 글·사진 테이블을 만듭니다.
- `V7__image_deletion_jobs.sql`: 파일 삭제가 실패해도 다시 시도할 수 있는 작업 테이블을 만듭니다.
- `PostImageService`: 사진 순서를 검증하고 파일 저장·교체·삭제를 DB 커밋 결과와 연결합니다.
- `PostDraftService`: 계정당 5개 제한, 마지막 저장 후 3일 만료, 게시 전 필수값 검증을 처리합니다.
- `PostService.delete`: 작성자를 확인한 뒤 게시글 행을 삭제하고 커밋 후 사진 파일을 정리합니다.
- `ExpiredDraftCleanup`: 만료된 임시저장 글과 사진을 주기적으로 정리합니다.
- `ImageDeletionQueue`·`ImageDeletionRetry`: DB 커밋 후 파일 삭제를 시도하고 실패한 작업을 다시 처리합니다.

## 사진 요청

게시글 등록·수정은 `multipart/form-data`를 사용합니다.

- `post`: JSON 객체 `{ "title": "...", "description": "...", "price": 1000 }`
- `images`: 새 JPEG·PNG 파일 0~5개. 같은 이름으로 여러 번 넣습니다.
- `order`: 최종 사진 순서의 JSON 배열. `e:0`은 요청 전 첫 번째 사진, `n:0`은 이번 요청의 첫 번째 새 파일입니다.

예를 들어 기존 사진 두 장 중 두 번째를 대표 사진으로 바꾸고 새 사진 한 장을 끝에 붙이면 `["e:1","e:0","n:0"]`입니다. 배열에서 빠진 기존 사진은 삭제합니다. 서버는 중복·잘못된 번호와 5장 초과를 거부합니다. 기존 단일 `image`·`removeImage` 요청도 계속 받습니다.

상세 응답의 `imageUrls`가 모든 사진의 순서입니다. `imageUrl`은 목록과 이전 클라이언트를 위한 첫 사진 주소입니다. 게시글 사진은 공개 조회되고 임시저장 사진은 작성자만 조회할 수 있습니다.

## 임시저장

새 임시저장은 `POST /drafts`, 다시 저장은 `PATCH /drafts/{id}`입니다. multipart의 `draft` JSON에는 제목·본문·가격을 비워 둘 수 있고, 사진은 게시글과 같은 `images`·`order` 형식을 사용합니다. 임시저장은 계정당 활성 글 최대 5개입니다.

`GET /drafts`와 `GET /drafts/{id}`는 작성자에게만 열립니다. 마지막 저장 시각부터 3일이 지난 글은 조회·수정·게시할 수 없습니다. 만료 행과 파일은 주기적으로 정리합니다. 작성자가 `DELETE /drafts/{id}`를 요청하면 바로 삭제합니다.

게시할 때는 `POST /drafts/{id}/publish`에 현재 입력한 `post` JSON, `images`, `order`를 multipart로 보냅니다. 게시 버튼은 임시저장을 호출하지 않습니다. 서버는 필수값을 검사하고 게시글을 만들며, 사진 소유권을 게시글로 옮기고 임시저장 글을 제거합니다. 실패하면 DB 작업과 새 파일 저장을 롤백하고 이전 임시저장본을 유지합니다.

작성 화면의 닫기/X는 서버에 저장 요청을 보내지 않습니다. 이미 저장된 마지막 임시저장본만 남습니다.

## 삭제와 파일 정리

`DELETE /posts/{id}`는 작성자만 호출할 수 있고 게시글 DB 행과 사진 연결을 영구 삭제합니다. 파일 삭제 작업은 같은 DB 트랜잭션에 기록하고 커밋 후 즉시 처리합니다. 실패한 작업은 주기적으로 재시도합니다. 새 사진을 저장한 직후 프로세스가 강제 종료되면 아직 DB에 기록되지 않은 파일이 남을 수 있으므로, 운영에서는 저장소 잔여 파일 관측이 필요합니다.
