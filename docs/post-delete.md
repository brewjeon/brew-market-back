# 게시글 삭제 API

## 개발 목적과 선택

작성자가 더 이상 공개하고 싶지 않은 글을 숨길 수 있게 합니다. 향후 신고·약속 기록과 연결할 가능성을 고려해 DB 행을 지우지 않고 `deleted_at`에 삭제 시각을 기록합니다. 이 기능은 공개 게시글의 삭제 표시이며 개인정보의 영구 삭제나 회원 탈퇴를 대신하지 않습니다. 보관 기간·영구 파기·관리자 접근·복구 기능은 별도 정책이 필요합니다.

현재는 거래 상태와 관계없이 작성자가 삭제할 수 있습니다. 향후 약속이나 거래가 연결되면 진행 중인 약속을 취소하지 않고 글만 숨겨도 되는지 정책을 추가해야 합니다.

## 요청과 응답

`DELETE /posts/{postId}`. 요청 본문은 없습니다. 로그인 세션과 현재 세션의 CSRF 토큰을 보내야 합니다. 회원 번호는 로그인 정보에서 가져옵니다.

| 조건 | 응답 |
|---|---|
| 작성자의 최초 삭제 | 204, 본문 없음 |
| 다른 회원의 삭제 | 403, POST_ACCESS_DENIED |
| 없는 글 또는 이미 삭제된 글 | 404, POST_NOT_FOUND |
| 비로그인, 유효한 CSRF 포함 | 401 |
| CSRF 누락·불일치 | 403 |
| 같은 버전을 읽은 수정·삭제가 충돌 | 409, CONCURRENT_MODIFICATION |

삭제 후 목록에서 제외되며, 상세 조회·수정·반복 삭제는 모두 404입니다. 반복 요청의 응답은 달라도 최종 삭제 상태는 유지됩니다. 거래 상태를 COMPLETED로 바꾸지 않습니다. 거래 완료와 게시글 삭제는 다른 사실입니다.

목록은 DB 조회에서 삭제 여부를 먼저 필터링한 뒤 최신 20개를 가져옵니다. 먼저 20개를 가져온 후 메모리에서 삭제 글을 빼는 방식이 아닙니다.

## 생성·변경 파일과 목적

| 파일 | 목적 |
|---|---|
| `V4__add_post_deletion_and_version.sql` — 신규 | 기존 posts에 삭제 시각과 버전 컬럼을 추가합니다. 기존 글은 삭제 시각 null, 버전 0으로 유지됩니다. |
| `Post.java` | 삭제 시각 기록, 삭제된 객체의 내용 변경 거절, `@Version`으로 오래된 상태의 저장 방지 |
| `PostRepository.java` | 삭제되지 않은 단건·최신 20개 조회 정의 |
| `PostService.java` | 조회·수정·삭제의 활성 게시글 조건 공유, 작성자 확인 후 삭제 표시 |
| `PostController.java` | DELETE 요청을 서비스에 연결하고 204 반환 |
| `SecurityConfig.java` | DELETE 경로에 로그인 필수 적용, 기존 CSRF 보호 유지 |
| `PostAccessDeniedException.java` | 수정·삭제에 공통으로 사용할 작성자 권한 오류 메시지 |
| `GlobalExceptionHandler.java` | 버전 충돌을 409 응답으로 변환 |
| `README.md`, `docs/post-update.md` | 삭제 계약 연결 및 수정의 동시성 설명 갱신 |

## 수정·삭제 충돌을 다루는 이유

수정 요청 A와 삭제 요청 B가 같은 글을 읽으면 둘 다 삭제 전 객체를 갖습니다. 버전 검사 없이 전체 필드를 저장하면 A가 나중에 저장하면서 B의 삭제 시각을 null로 덮어쓸 위험이 있습니다.

`@Version`은 저장 시 읽었던 버전을 조건에 포함하고 성공하면 버전을 올립니다. 먼저 반영한 요청 이후에 예전 버전으로 저장하는 요청은 실패하며 트랜잭션이 롤백됩니다. 클라이언트는 409를 받으면 다시 조회해 현재 상태를 확인해야 합니다. 구버전 애플리케이션은 버전 검사를 하지 않으므로 운영 배포 시 모든 쓰기 인스턴스의 호환성을 따로 확인해야 합니다.

## 적용·검증 상태

V4 파일 작성만으로 실행 중인 DB가 바뀌지는 않습니다. 다음 애플리케이션 시작 시 Flyway가 적용한 뒤 Hibernate가 매핑을 확인해야 합니다. 이번 작업에서는 서버·DB 마이그레이션과 테스트를 실행하지 않습니다.

이 브랜치는 아직 main에 병합하지 않은 `feat/post-update`에서 분기했습니다. 삭제 작업을 main과 비교하면 수정 기능도 함께 보입니다. 삭제 변경만 검토할 때는 `feat/post-update`와 비교하고, 이후 병합 순서는 수정 → 삭제로 잡습니다. PR은 생성하지 않았습니다.
